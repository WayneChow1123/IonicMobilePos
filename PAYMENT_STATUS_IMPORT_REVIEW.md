# Invoice payment status and master-data Excel import — 2026-11-11

## Payment status

Terms and payment state are separate. Changing Cash Sale / On Credit / Net 30 Days
does not create or delete payment records. Status is derived from actual remaining
payments, applied credit and debt-offset return CNs. No outstanding amount is Paid;
some payment/credit with an outstanding amount is Partial; otherwise it is Unpaid.
Refund/change CNs that become available customer credit are not deducted as debt offsets.

The previous DeletePayment path subtracted the payment, then queried Payments before
the deletion was committed and counted that same payment again. The API now explicitly
excludes it while calculating the remaining payments. Invoice list/report reconciliation
also repairs stale cached paid totals from old deletions; it does not recreate missing
payments. Invoice editing no longer marks Cash as paid without recording a payment.

The app uses amount-based status badges, preserves payment amounts on term edits,
updates list/detail caches after online and offline payment deletion and ignores legacy
local paid/status/balance overrides. Payment List selection uses the same amount rule.
The API and app must both be updated; existing APKs retain their old UI logic.

Manual regression:

1. Create a test RM100 On Credit invoice; record RM100 payment. Switch to Net 30 Days.
   It must remain Paid, with the original payment still in Payment List.
2. Delete that payment. Invoice Report, details, export and print must show RM0 paid,
   RM100 due and Unpaid without editing terms. Close/reopen the app and verify again.
3. With RM40 and RM60 payments on a RM100 invoice, delete RM60. Expect Partial,
   RM40 paid and RM60 due. Changing terms must not change these amounts.
4. Repeat payment deletion offline with previously cached data, restart, reconnect and
   check the server. Applied credit / full return cases can legitimately have zero
   balance without a cash payment.
5. Historical Paid invoices with no actual payment record will now reconcile as Unpaid
   when money remains due. This is intentional; no payment records are fabricated.

## Import Excel

Preferences → Import Excel supports Products and Customers, not invoice import.
Download the selected template, add rows below its header, select the `.xlsx`, review
validation and skipped duplicates, then press Confirm Import. Limits: 10 MB and 2,000
data rows. Use text cells for barcode, phone and codes so leading zeros are preserved.
Formula cells are rejected. Product Price and Name are required; Customer Name is
required. Required template headers must remain present even for blank optional cells.

Products: Name, Barcode, Category, Uom, Price, Rate, Cost, Lowest Price, Stock,
Include Tax, Description. Customers: Name, Phone, Email, Address, Customer Category,
Term, Discount Percent, Enable Discount, Require Digit Sign, Description. New codes
are generated by the existing API; optional Code / Customer Code columns can identify
existing records to skip. This initial import does not overwrite or merge existing data,
import opening credit/debt, import branches or import special prices.

Duplicate matching uses product Code/Barcode (or name when barcode is absent), and
customer Code or name + phone. It checks within the file, against available device/server
records at preview, and again before confirmation. Offline checking cannot see server
records never downloaded to the device; normal server validation still applies on sync.
All invalid rows must be corrected before confirmation. Successfully saved rows are
never sent again on retry; failed rows remain retryable with their operation identity.
Queued rows are labeled Pending API sync. Storage and server validation failures are
not reported as successful imports. Import is sequential, so a partial failure retains
per-row results instead of implying an all-or-nothing database transaction.

Test on staging first with two products (one duplicate) and two customers; inspect data,
numbers, booleans, discount, leading zeros, offline restart/reconnect, API persistence,
and retry after a rejected row. Native Android file selection still needs a device test.

Validation logs: payment-import-tests.log (browser regression suite),
payment-import-build.log (production Angular build), and payment-import-final-sql.log
in the API integration-test folder (disposable SQL LocalDB tests). No live API calls,
live database operations, deployment, APK installation or Git push were performed.

## Product/customer export and import controls

Preferences now labels the entry Import / Export Excel. Select Products or Customers and use Export Products Excel / Export Customers Excel to download current available records in the import format, including existing codes. Blank templates remain available. Exported files larger than 2,000 data rows must be split before importing. Existing records are skipped, so exporting, editing and reimporting does not overwrite existing records. Barcode/phone text and numeric/boolean values are preserved, including valid negative stock.

The Back control now shares the standard black chevron style. The data type control opens a centered selection dialog with Products/Customers options and Select/Cancel actions, and the hidden native file input is opened by a styled Choose Excel File button with filename display. Native Android file/share dialogs still need device testing.

## Export Bills customer selection — 2026-11-12

By Customer now uses the Create Payment-style full-screen customer selector: safe-area header, close action, search by name/code, customer icon/code cards, selected highlight and empty results. Selecting a customer updates the invoice list and preserves export of all invoices for that customer. The native HTML select is removed. Search and selected-customer export are covered in the browser suite (90 passing tests).
