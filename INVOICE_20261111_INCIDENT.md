- APK installed over the existing app, not deliberately uninstalled.
- User reports no 2026-11-11 invoices in the database and none visible on the original phone.
- API deployments were on November 6 and November 12.
- Client describes creating invoices and not finding them in Invoice Report.
- User says the incident concerns the November 11 batch; a current creation displays
  Invoice Created. This message alone does not establish current database persistence.
- Client subsequently confirmed working and creating invoices OFFLINE on both November 11 and November 12.
  Both days lack server invoices according to the user. November 13 offline work has not been established.
  Investigation must prioritize original-device local orders and sync receipts, rather than presume server deletion.

## Source review

No day-specific bulk deletion was found in the reviewed startup, invoice creation,
invoice payment reconciliation or sync paths. Actual invoice deletion has an explicit
endpoint and queued DELETE_INVOICE path; server logs are needed to determine whether
either ran. Source inspection cannot establish what happened to the live database.

The latest release reviewed did not change the app ID, WebView configuration, local
IndexedDB names/versions or local storage service relative to the preceding pushed
release. The actual deployed APK/configuration and client device still need comparison.

Found a separate confirmed protection gap: the client accepted a successful HTTP
response without requiring a valid invoice ID. The UI could clear the draft and show
Invoice created despite no confirmed identity. There is no captured November 11
response demonstrating this was the incident cause.

## Local safeguards added, not deployed

- Normal and queued creation reject acknowledgements without a positive integer ID.
- An invalid acknowledgement cannot be considered a successful queued upload.
- UI stores/reuses the invoice reference and number in the draft before sending.
  Retrying an uncertain result keeps the same reference for server deduplication.
- Existing duplicate acknowledgements show an existing-invoice message.
- 93 browser tests passed; production Angular build passed. No missing invoices have
  been recovered, no live server/database call was made, and no Git push was performed.

## Evidence and recovery path

1. Preserve the original device, current database and deployment/access logs. Avoid
   clearing app data, reinstalling or manually recreating invoices before reconciliation.
2. Have the host administrator run INVOICE_20261111_READ_ONLY_CHECK.sql from the API
   repository against the database actually used by the deployed API. It examines daily
   counts, number/date clues, successful-create replay receipts and restore history.
3. A successful create receipt whose invoice no longer exists supports investigation
   of deletion/database replacement/restoration. No receipt does not prove no upload:
   earlier clients, another database, missing headers or missing history are alternatives.
4. Where WebView inspection is already available, collect-invoice-evidence.js can read
   existing order/item/payment stores, sync tasks, invoice caches and fallback/draft data
   from the affected app context without API calls or restore/sync actions. It is a
   diagnostic helper, syntax-checked but not run on the client's device. Do not uninstall
   the app merely to enable inspection. Preserve its output before any recovery attempt.
5. Reconcile invoice references, payments, credit notes and stock against server evidence
   before re-importing local copies or restoring backups. Restore testing belongs in a
   separate database, not over live data. There is no automatic recovery in this change.

## Mixed invoice numbers

INV-T106-20261110105009-55 is the raw number generated by generateInvoiceNumber; both online and offline create paths use it. Successful sync can preserve that number. 2026111003 matches the daily display DOC NO format. Existing invoice edit code initializes the editable number from docNo before invoiceNumber and can persist that display value through UpdateInvoice. Both formats in the database are therefore possible; neither is a sync-status indicator. Match by ClientId / OfflineReferenceId / server Id and actual dates, not the INV prefix alone. No source change to numbering or bulk recovery is made during this incident.
